# Единый выпуск сайта

Один выпуск определяется тройкой **полный SHA коммита → build ID → SHA-256 архива**.
Обе площадки получают один `site.zip`, собранный один раз в CI. Сервер не пересобирает
опубликованный выпуск. `build.json` содержит `source_commit`, поэтому совпадение
текста или версии правил само по себе больше не считается совпадением выпуска.

## Подготовка без публикации

Push в `main` и pull request запускают только `.github/workflows/ci.yml`,
**Prepare site candidate**. Изменения только Markdown, `docs/**` и `.impeccable/**`
на push пропускаются. Для актуальной `main` можно вручную запустить этот CI.

CI собирает сайт с полным SHA исходников, выполняет JavaScript- и Python-тесты,
`scripts/verify.py` и создаёт артефакт `site-candidate`, сохраняемый 30 дней:

- `site.zip` — все файлы сайта, включая PDF и увеличенные изображения;
- `release.json` — коммит, build ID, SHA-256 и размер архива, хеш каждого файла.

Пакет создаётся только из чистого коммита. Перед использованием проверяются
внешний SHA-256, состав ZIP, каждый файл, офлайн-манифест и `source_commit`.
Разрешены только публичные относительные пути; ссылки и дубли файлов отклоняются.
Архивы, служебные данные и секреты не включаются в сайт.

Итог CI показывает точный кандидат и готовую SSH-команду. На этом этапе
GitHub Pages, основной `dist/` и серверные исходники не обновляются.

## Подтверждение

До запуска публикации показать владельцу коммит, build ID, SHA-256 архива,
результаты проверок, обе площадки и способ отката. Требуется подтверждение именно
этого кандидата. Предыдущее разрешение и зелёный CI не являются подтверждением.

`.github/workflows/pages.yml`, **Publish approved build**, запускается только
вручную из `main`. Требуются SHA исходников, SHA-256 пакета, номер успешного CI
и флажок `confirm=true`. Workflow разрешён только владельцу репозитория.
Без подтверждения ни один job публикации не выполняется.

Для нового выпуска CI должен быть успешным запуском `push` или `workflow_dispatch`
на `main` в этом репозитории, с тем же SHA и нужным workflow. Запуски pull request
не принимаются как источник публикации.

## Одна последовательность для обеих площадок

После подтверждения:

1. Через проверенный SSH-вход выполнить **дословную команду из Summary CI**.
   Она запускает `tools/release_main.py apply` с SHA коммита, build ID, SHA-256,
   `--confirm --wait-seconds 1200`. Это разовая команда, не постоянная служба.
   Оставить процесс работающим до завершения. Он проверяет чистоту серверной `main`,
   происхождение коммита и возможность fast-forward, затем ожидает конкретный выпуск.
2. Запустить **Publish approved build** с параметрами того же кандидата.
   `published_release` оставить пустым. Workflow проверяет CI, пакет и свежую
   готовность серверного процесса до каких-либо изменений Pages.
3. Workflow сохраняет подтверждённый пакет в GitHub Release с тегом
   `site-<source_commit>-<build>`. Все файлы сначала загружаются в черновик;
   только полный набор `site.zip`, `release.json`, `approval.json` становится публичным.
   Опубликованные файлы этого процесса не заменяются.
4. Сервер скачивает этот же ZIP в `Share`, проверяет все хеши, сохраняет полный
   прежний `dist/` и проверяет восстановление. Новая сборка готовится отдельно.
   Подтверждение готовности появляется только после этой подготовки.
5. Только получив готовность сервера, workflow переносит готовые файлы на Pages.
   Он не запускает сборщик повторно.
6. Сервер дожидается именно этого коммита и build ID на Pages и проверяет ресурсы.
   Затем атомарно меняет основной `dist/`, синхронизирует серверную `main` с
   утверждённым коммитом и проверяет обе площадки. При ошибке переключения или
   проверки основного сайта возвращает прежние файлы и исходники.
7. После проверки и переноса резервной копии в `Share` сервер публикует служебный
   `deployment-status.json` с состоянием `verified`, SHA исходников, build ID
   и SHA-256 пакета. Workflow требует именно это подтверждение, затем проверяет
   все ресурсы обеих площадок. Только после этого выпуск успешен.

Нельзя заменять указанную команду произвольными `git pull`, сборкой в рабочем
`dist/` или ручным копированием отдельных страниц. Незавершённые серверные правки
останавливают процесс и сохраняются. Параллельные серверные операции блокируются
файловой блокировкой; workflow публикации выполняется последовательно.

## Серверные файлы и данные

- Проект: `/mnt/Hosting/kostya/bronepehota`.
- Действующий сайт: его `dist/`; временный кандидат — `.deploy-<build>` рядом.
- Архивы, операции и копии: `/mnt/Share/kostya/bronepehota`.
- Исполняемые Python-инструменты: `tools/release_main.py`, `release_bundle.py`,
  `release_workflow.py`, `deploy_main.py`, `verify_deployed.py` в этом хранилище.
- Состояние операции и резервный TAR: `deployments/<build>/`.

SSH-ключ хранится локально. GitHub не получает ключ или доступ к серверной оболочке.
Сервер скачивает публичный, уже подтверждённый выпуск. Постоянные таймеры,
webhook, новые учётные записи и изменение Nginx для этого процесса не нужны.

`deployment-prepared.json` — краткоживущая готовность разового процесса;
`deployment-status.json` — подтверждение завершения. Это служебные файлы только
основного сервера: они исключены из ZIP, офлайн-манифеста и сравнения статических
файлов. Их наличие не изменяет артефакт общих страниц и ресурсов.

## Ошибки, повтор и откат

Подготовка и готовность сервера проверяются до обновления Pages. Если этот этап
не пройден, действующие сайты остаются прежними. Незавершённый черновик GitHub
Release требует проверки; процесс не перезаписывает его вслепую.

Две площадки переключаются последовательно, поэтому во время выпуска возможен
переходный период. Ошибка после переключения Pages не выдаётся за общий успех:
workflow завершается ошибкой, основной сервер сохраняет или восстанавливает
предыдущую сборку. Следует завершить тот же подтверждённый выпуск повтором либо
восстановить предыдущий общий выпуск на обеих площадках. Не начинать следующий
выпуск, пока предыдущая операция не разобрана.

Для возврата к **непосредственно предшествующему общему выпуску**:

1. Взять его точные параметры из сохранённого GitHub Release и подтвердить откат.
2. Запустить ту же разовую серверную команду с параметрами старого выпуска,
   добавив `--rollback`. Сервер проверит соответствие своей резервной копии,
   подготовится, затем дождётся старого выпуска на Pages.
3. В **Publish approved build** указать его тег в `published_release`, старые
   `source_commit` и `bundle_sha256`, `confirm=true`. `candidate_run` не требуется:
   используется сохранённый подтверждённый Release, даже после истечения CI-артефакта.
4. Дождаться успешной проверки обеих площадок. Серверные исходники и основной
   сайт вернутся к одному коммиту и пакету; история GitHub не переписывается.

До первого общего выпуска площадки остаются на исторических сборках
`65b13840439b7db8` и `77b555bd60c5ac9e`. Настройка процесса сама их не публикует
и не выравнивает. При первом подтверждённом выпуске сохранить прежние данные
обеих площадок; основной сервер делает полную резервную копию автоматически.
Для исторического восстановления основного сайта сохраняется
[проверенная процедура](deployment-main.md). Схема общего отката выше относится
к выпускам нового процесса, а не к прежним отдельным сборкам.

## Основания и проверки

Ручной запуск основан на [workflow_dispatch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
Повторное использование артефакта другого запуска — на
[actions/download-artifact](https://github.com/actions/download-artifact#download-artifacts-from-other-workflow-runs-or-repositories).
Пакет сохраняется через [GitHub Releases API](https://docs.github.com/en/rest/releases/releases).

Тесты: `tests/test_release_process.py`, `tests/test_verify_deployed.py` и прежние
проверки сайта. Они проверяют неверный SHA/коммит, повреждение пакета, пути,
отсутствие подтверждения, устаревшую готовность, запрет ложного успеха, откат,
сохранность чужих правок и реальные атомарные переключения на Linux.
Полная публикация нового общего выпуска проверяется только после подтверждения;
тестовый прогон на изолированных каталогах не выдаётся за такую публикацию.
